## 步骤及数据完整性

1. 备份仓库文件、HEAD、索引、status 与应用设置；使用独立 profile 启动测试程序，打开上述场景。
2. 等待 20 秒，取得 baseline。随后六轮各持续 30 秒，每秒写入活动文件一次，再恢复原字节并等待 15 秒，取得 recovery 样本。
3. 六轮各 30 次，共 180 次负载写入，另有六次恢复写入；六次均报告恢复成功、无写入错误。最后静置 90 秒，取得 final。
4. 每个堆样本记录 GC 前后的 heap/DOM 计数，并执行两次强制 GC，间隔 400ms。baseline/final 保存完整堆快照。DOM 诊断只返回标量，不保留远端对象句柄。
5. 原生右键标签选择 Close All Tabs，确认只剩 Workspace，再取得 closed-tabs 样本与快照。此步骤在正式六轮采样结束后进行。
6. 进程采样持续 395.691 秒，得到 132 点；7 个持续进程身份各有完整 132 点。另有 57 次 `ProcessCommandException` 跳过记录，未得到其完整身份，不能声称捕获了所有短命子进程；不把它们补算为零开销。

六轮及 final 的连接 DOM 元素均为 856，CSS 规则均为 272 条/83,977 字符，活动文件内容恢复为 `changed 2`，任务状态恢复 Idle。关闭标签后连接元素为 792，CSS 规则数量及字符数保持；没有观察到样式随刷新累积。

final 的 GC 后 JS heap 比 baseline 多 1.025 MiB，recovery-6 至 final 只相差 96 bytes。关闭三个标签后又减少 0.861 MiB。这里证明了本场景存在可回收分配及标签关闭后的释放；不能将这些差值直接视为某个组件的精确 retained size。

## 快照分类核查

分析器按运行时提供的节点/边字段读取快照并校验边计数；比较构造器时去除 snapshot-local `scope @数字` 后缀，避免把作用域标识变化误算为新增对象。快照 self size 与 Runtime heap 统计不是同一口径。

| baseline → final 分类 | 数量变化 | self size 变化（bytes） |
| --- | ---: | ---: |
| code | -579 | +1,015,780 |
| native | +2952 | +196,165 |
| object | +80 | +268 |
| array | +151 | +1,872 |
| closure | +1 | +28 |
| string | -770 | -10,048 |
| concatenated string | -289 | -5,780 |

code 类中的主要正增量是 `system / InstructionStream` +835,008 bytes 和 `system / TrustedByteArray` +244,780 bytes；还有负增量，不能只把正项相加当净增长。native 的变化包含 WeakArrayList、DOMRectReadOnly、LayoutShift/Attribution 等。此为快照分类证据，不把运行时内部对象增量直接归因为产品泄漏，也不宣称已获得全部保留路径。

两个快照中 detached 节点均为 121/self size 13,480 bytes，关闭标签后降为 55/6,168 bytes。关闭前后普通 object 减少 9589 个，closure 减少 3811 个。与 DOM、监听器结果结合，本轮没有发现随六次刷新累积的编辑器/DOM/监听器泄漏。

按 `id/line/stream` 属性识别的控制台条目在三份快照中均为 2 条，直接 line 节点大小均为 80 bytes。没有支持“本轮增量来自控制台逐渐填满”的证据；这是结构识别结果，没有据此声称完成控制台根引用的 retained-size 归因。
