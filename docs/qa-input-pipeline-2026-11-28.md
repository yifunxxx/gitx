# QA008/034：历史滚动断档的输入链核对

日期：2026-11-28。开始前读取台账、fetch及master/交付分支检查成功，干净基线 `a5d3d7828887e474aa02d532d4cddba83d991df2` 包含master `50a4802dd23f61055668e165f6fe7c0b93b17680`。全程主线程，本轮没有产品修改、新构建或新原生输入。

## 新证据与实际结论

重析[11月26日连续输入](qa-native-scroll-delivery-2026-11-26.md)四组有效trace，将此前只到滚动更新/呈现的分析向前扩展到浏览器鼠标处理入口、Wheel构造及渲染线程接收。四组都显示长空档已经存在于浏览器`RenderWidgetHostViewBase::OnMouseEvent`的相邻调用之间；该入口之后已进入的Wheel并没有同等秒级等待。

这把**这些历史样本中的长空档**定位到已记录浏览器入口之前或入口之间尚未记录的处理，而不是证实前端收到输入后卡住8秒。仍不能区分工具后台递送、Windows消息排队、GitX宿主或WebView未覆盖的路径，也不能把采样工具成功返回视为操作系统已完成发送。没有逐次工具调用与原生消息的共同身份，不能进一步认定某个组件是根因。

## 方法与有效性

- 原始程序实际版本仍为0.1.49、WebView158.0.4370.33，全部数据来自11月26日，不冒充当前0.1.56复测。四份trace SHA256逐份与当日分析记录核对一致。
- Python整数保留有符号64位`trace_id`；输出身份转字符串。`InputLatency::MouseWheel`与渲染侧`EventLatency(MOUSE_WHEEL)`用完整trace身份关联，不按相邻序号或相近时间猜测。
- `BEGIN_RWH`时间必须唯一落在同PID/TID的`ForwardWheelEvent`范围内；浏览器`OnMouseEvent`必须唯一包含该转发范围，其内必须有唯一`WebMouseWheelEventBuilder::Build`。这是明确的同线程范围关联，不是跨线程身份关联。
- `LatencyInfo.Flow`的接收阶段也按完整trace身份关联，核查时间顺序、无重复阶段，统计浏览器入口到最早渲染侧接收的时间。所有264个有Builder的Wheel都被覆盖。
- 另外11条Wheel没有上述入口，逐条确认转发位于`SendSyntheticWheelEventWithPhaseEnded`范围内，且没有UI时间组件；作为浏览器合成的结束事件排除。静态第一组最长间隔内有1条这样的合成结束转发，不能声称间隔内完全没有任何输入事件；其他三组间隔内上述入口/Builder/转发均为0。
- 异步范围按名称、类别、PID、scope及id/id2类型配对；重复开始、孤立结束、未闭合、阶段歧义都会失败。最初把全部OnMouseEvent数等同于Wheel数、把间隔内任何转发都视为Wheel的假设被真实数据否定，已改为逐事件范围核对并单列合成结束，没有删原始事件或强行放宽时间阈值。
