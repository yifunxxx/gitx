# QA040/008：有 CPU 增量的宿主线程栈

日期：2026-11-26。接续[连续滚动输入递送报告](qa-native-scroll-delivery-2026-11-26.md)。开始前读取台账，fetch 及 master/交付分支检查成功，基线 `aa264dadca99496b21325137e4879b0f712883b5` 包含 master `84ececc`（0.1.50）。全程主线程，未修改产品代码。

## 本次新增证据

旧 `qa040-idle-stacks-20261124` 的正式采样中，三条线程 CPU 增量均为零，不能解释先前高占用。本轮先按进程/线程累计 CPU 增量选择热点，再采集调用栈，并复核采栈期间是否仍有 CPU 增长。

主线程在五组采栈期间实际增加 0.703125–1.53125 CPU 秒；稳定阶段的另一热点线程也有增长，其可信栈前缀出现 `UIAutomationCore!ChannelBasedServerConnection::ProcessOneMessage`、`ProcessIncomingRequest`、`ProviderEntryPoint::TryGetInProcNativeUiaNode`。主线程也抓到过 `RemoteUiaNodeStub::Incoming_GetPropertiesAndPatterns` 与 `InProcClientAPIStub::UiaNode_GetPropertiesAndPatterns`。

这比只有等待栈增加了请求处理路径证据，但尚未确认客户端身份，也未在本轮重现上轮 8.562 秒输入断档。不能把所有 CPU 归给 UIA、把等待栈比例当作 CPU 占比，或认定产品没有问题。

- 复用上轮独立 Windows debug 程序，实际版本 **0.1.49**，产品逻辑基于 `5bea847`；与当前基线相比仅版本清单/文档变化，未冒充 0.1.50 重新构建。

- 每约 1.5 秒读取一次进程/线程 CPU，核对 PID/TID 和创建时间。总进程超过 0.12 核且线程超过 0.04 核时，选择最多三条线程。
- 使用既有只读 `stack-snapshot.exe`，每组 30 次 PSS VA clone/线程上下文快照，间隔 211ms；使用本地匹配符号，StackWalk64 读取快照，不注入、不写目标内存、不手工暂停、不调试附加。

- 部分栈只有一帧或展开到未解析地址。分析在首个未知模块处截断，后续帧不计入可信 UIA 路径；保留原始栈，不能据不完整栈断言不存在业务调用。

## 单次原生滚轮诊断

原生双击打开 `group-00/file-0000.txt` 普通双栏差异后，在 Commit 视口调用一次 `scrollY:3600`，随后仅截图。CDP 仅用于 trace 和前后只读几何，没有合成输入、修改 DOM 或调用产品 store。

该调用实际只得到一次 `FIRST_GESTURE_SCROLL_UPDATE`（两条 MouseWheel），列表从0移动至305px，恰为一页。唯一严格关联呈现延迟13.826ms；异步配对问题0，`dataLossOccurred=false`。**这不是连续滚动测试**，不能以较大参数或一次较低呈现延迟补齐 QA008，也不能复现或解释上轮断档。热点快照在这一事件之后，不能标作断档同期栈。

本轮新的可执行方向是保留热点触发与同期间 CPU 复核，在真正断档期间取得宿主消息/客户端身份；现有方式缺少内核消息处理栈与来源。旧UIA ETW曾遭 Access denied，本轮没有重复同样无权限尝试、提升权限或改变系统安全设置。继续其他已授权功能/逻辑检查，不以重复相同短样本代替归因。
