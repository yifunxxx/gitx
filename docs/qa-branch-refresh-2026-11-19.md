# QA-034：分支信息刷新引起文件树重复构建

2026-11-19，基线为 `5ff1828`（0.1.40，包含路径树与收起分组优化）。本轮继续核查后台刷新期间的主线程工作，确认一个可独立消除的重复计算来源。它是 QA-034 下的定向优化，不代表所有滚动停顿已经解决。

## 现象与修改

在文件列表完全相同的情况下，仅 `branch.behind` 从 0 变为 1，也会替换整个 StatusSnapshot。原来五个文件分类直接依赖快照外壳，每次产生新数组，继而令 ChangesTree 重建展开的树、平铺排序和全部行对象。相同分支与文件的普通版本刷新已有去重，但分支元数据变化不在其覆盖范围内。

现在先独立判断同仓库的文件列表是否相等。若仅分支信息变化，快照继续更新分支信息，同时复用之前的文件数组；不修改后端返回对象。分类通过稳定的文件数组 computed 读取数据，避免快照外壳变化引起文件模型失效。分支信息仍传给 workspace；文件路径、重命名来源、状态、种类、数量或顺序变化仍正常更新，仓库切换仍重置状态。后台变更列表读取、勾选清理及版本过期保护保持有效。

## 受控对照

用 Node 24.22.1 加载真实 changesStore.ts，以及 Vue SFC 编译后的 ChangesTree.vue setup，运行真实 Vue/Pinia 响应式与 watcher。输入为 20,000 个嵌套路径、同时具有暂存和未暂存修改的文件；每次后端返回新对象，只有 behind 字段变化。组件 setup 测量不含 DOM 渲染、原生事件或呈现。

| 模式 | 分支刷新建树处理文件数，修改前 → 后 | FileChange.path 读取次数，修改前 → 后 | 行对象数组 |
| --- | ---: | ---: | --- |
| 暂存 / 树形 | 40,000 → 0 | 120,000 → 40,000 | 40,805 行重建 → 保持引用 |
| 暂存 / 平铺 | 不建树 | 120,000 → 40,000 | 40,003 行重建 → 保持引用 |
| 变更列表 / 树形 | 20,000 → 0 | 80,000 → 40,000 | 20,403 行重建 → 保持引用 |
| 变更列表 / 平铺 | 不建树 | 80,000 → 40,000 | 20,002 行重建 → 保持引用 |

修改后的 40,000 次路径读取来自新旧 20,000 个文件逐一比较，未声称状态刷新零开销。暂存树形原来调用建树 3 次（含一个空分组），变更列表树形调用 2 次（含一个空分组）；修改后均为 0。五个分类数组和 rows 均保持原引用，workspace 的 behind 正确变为 1。真正修改最后一个文件的 worktreeStatus 后仍重建，并正确更新暂存模式的行数。

单次诊断计时，暂存树形分支刷新为 122.201 → 9.292 ms，变更列表树形为 75.524 → 8.493 ms。这不是多轮统计、原生滚轮时延或用户仓库性能承诺；本次可靠对照结论是上述重复工作与对象替换被消除。
