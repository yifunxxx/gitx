# QA131 删除失败与草稿保护

## 来源与基线

沿File右键/移动/拖放的失败处理审阅发现，`fileOperationsStore`在用户确认丢弃草稿之后、调用磁盘删除之前直接把所有相关标签的`dirty`改为false。后端拒绝、部分成功或后续保存状态检查中止时，仍存在的文件会失去未保存标记；之后保存可能直接返回成功而不写入，关闭也不再提示。

开始前读取台账、fetch及master/交付分支检查成功，干净基线 `9cb449a` 包含master `50a4802`（0.1.56）。全程主线程，没有子代理。该发现独立登记QA131，不归因为原生拖放输入工具限制或滚动卡顿。

## 复现与修复

- 新增真实fileOperations/fileViewer/jobs联合测试，原实现10项中7失败/3对照通过，既有相关51项通过/1既有probe跳过。
- 失败覆盖调用拒绝、返回失败列表、整个等待期间dirty丢失、文件及目录部分成功、确认期间启动保存导致删除中止，以及确认期间新编辑被旧确认关闭。
- 保持草稿与dirty状态完整，确认只记录标签实例及当时正文；后端明确列为删除成功的文件才处理标签。内容仍一致的已确认草稿可关闭；失败项不动，新编辑及同ID的新标签实例保留，已删除文件继续显示相应提示并拒绝覆盖保存。
- 不通过清空dirty传递丢弃许可；许可仅属于当前删除调用，完成后释放。文件操作、任务队列、取消、导航归属、保存互斥及移动路径重映射保持原有机制。
- 既有mock用例返回空completed却要求清除dirty，其断言已纠正；成功关闭由真实store联合用例证明。中英文件教程补充失败保留及新草稿语义。
